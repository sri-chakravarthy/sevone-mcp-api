1. Technology Stack

Not FastMCP This server uses the low-level official MCP Python SDK (mcp>=0.9.0), not FastMCP.

LayerLibrary / ToolPurpose
MCP frameworkmcp (≥0.9.0) — official SDKProtocol handling, tool registration, stdio transport
HTTP clienthttpx (async)All REST calls to SevOne API
Credentialscryptography (Fernet)Symmetric AES-128-CBC encrypt/decrypt of password at rest
Configpython-dotenvLoads .env file (hostname, username, encrypted password, key)
Transportstdio (JSON-RPC over stdin/stdout)Bob spawns the server as a child process
RuntimePython 3.10+ / asyncioSingle async event loop; all I/O is non-blocking
FastMCP vs low-level SDK: FastMCP is a higher-level wrapper that lets you decorate plain Python functions with @mcp.tool() and infer schemas from type hints. This project uses the lower-level mcp.server.Server class directly — which means it wires up list_tools / call_tool handlers manually and defines inputSchema dicts by hand.

2. Architecture & Runtime Flow

Bob (parent process) │ spawns via .bob/mcp.json (stdio transport) ▼ venv/bin/python3 src/server.py │ ├─ SevOneMCPServer.__init__() │ ├─ mcp.server.Server("sevone-api") │ ├─ instantiates 10 Tool objects (one class per tool file) │ └─ registers list_tools / call_tool handlers │ ├─ SevOneMCPServer.initialize() ← called once at startup │ ├─ CredentialManager reads .env, decrypts password │ ├─ TokenManager stores creds; no network yet │ └─ SevOneAPIClient wraps TokenManager; no network yet │ └─ stdio_server() event loop │ │ (Bob calls a tool) ▼ call_tool(name, args) ├─ if/elif chain → routes to correct Tool.execute() ├─ Tool.execute() calls api_client.post/get/... │ └─ TokenManager.get_token() ← lazy; authenticates on first call │ POST /api/v3/users/signin → bearer token (cached 23 h) │ On 401 → invalidate + retry (up to 3×) └─ returns JSON-serialised TextContent to Bob

Authentication model

  • Password is Fernet-encrypted at rest in .env. A separate SEVONE_ENCRYPTION_KEY is needed to decrypt it.
  • Authentication is deferred — no network call happens at startup. The first tool invocation triggers a POST /api/v3/users/signin.
  • Token is cached in memory with a 23-hour TTL (5-minute safety buffer before expiry).
  • A 401 response automatically invalidates the token and retries up to 3 times.

Tool structure pattern

Every tool follows the same class shape:

class SomeToolName:
    @property def name(self) -> str          # string tool ID
    @property def description(self) -> str    # shown to LLM in list_tools
    @property def input_schema(self) -> dict   # JSON Schema (hand-written)
    async def execute(self, api_client, **kwargs) -> dict

The server.py call_tool() method is a plain if/elif dispatch chain over tool names.

5. Optimisation Opportunities

5.1 Eliminate redundant documentation in customInstructions

The tool descriptions defined in src/tools/*.py (e.g., all parameter descriptions in input_schema plus the description string) are already surfaced to Bob via the MCP list_tools response. You do not need to repeat them inside customInstructions.

Remove from sevone-get-details: the entire "Choose the Right Tool" section (lines 179–318) which re-documents every parameter of every tool. The LLM already sees these from the tool schema. Estimated saving: ~5,000 characters / ~160 lines.

5.2 Collapse example query patterns into a compact lookup table

The ~40 "User says X → use tool Y with args Z" examples in sevone-get-details are valuable but excessively verbose. They can be expressed as a compact two-column table:

# Instead of 40 prose blocks, use a short reference table:
| Intent keyword        | Tool                        | Key arg                         |
| find / get device     | get_device_details          | device_names or device_ids      |
| device group          | get_device_group_details    | device_group_ids or paths       |
| metadata IDs          | get_device_metadata_ids     | device_ids or namespace+attr    |
| objects               | get_object_details          | device_id / device_name         |
| indicators            | get_indicator_details       | device_ids / object_ids         |
| alert policies        | get_alerting_policy_details | name / alert_severities         |
| policy folders        | get_alerting_policy_folder  | (no filter needed)              |
Estimated saving: ~4,000 characters.

5.3 Move alerting-policy condition-decoding legend to tool description

The AND/OR delimiter legend, comparison/aggregation/type lookup tables, and example decoded sentences (lines 412–444) are decoding instructions for API response data, not mode-routing instructions. They belong in the get_alerting_policy_details tool's description property in src/tools/get_alerting_policy_details.py, so they only appear when that tool is actually listed.

Estimated saving: ~1,200 characters from the mode file.

5.4 Migrate to FastMCP to eliminate manual boilerplate in server.py

The current server.py has ~100 lines of manual wiring (instantiate 10 objects, build Tool() list, if/elif dispatch). With FastMCP the same is achieved with a decorator per function:

# FastMCP equivalent — entire server.py collapses to ~30 lines
from fastmcp import FastMCP

mcp = FastMCP("sevone-api")

@mcp.tool()
async def get_device_details(
    device_names: list[str] | None = None,
    device_ids: list[int] | None = None,
    ...
) -> dict:
    """Get device details from SevOne. ..."""
    return await _get_device_details_impl(api_client, ...)

FastMCP infers the inputSchema directly from Python type annotations, eliminating the hand-written JSON Schema dicts in every tool file.

5.5 Merge sevone-api-expert into sevone-get-details

The sevone-api-expert mode is a general-purpose "read Swagger and call run_api_endpoint" mode. In practice it overlaps heavily with sevone-get-details. Consider keeping only two modes:

Proposed modeCoverage
sevone-get-details (query)All read/query operations via typed tools + raw run_api_endpoint fallback
sevone-admin (write)All create/mutate operations
Eliminates one full mode definition (~120 lines).

5.6 Remove the "Common Query Patterns" prose duplication in sevone-get-details

The "Tips" block and the "Device/Object/Metadata/Policy Information Includes" sections at the bottom of sevone-get-details (lines 568–640) largely repeat what is in roleDefinition and whenToUse. Bob already reads all three fields. These can be cut to a single sentence each.

Estimated saving: ~1,800 characters.
